# 交叉参考：大侠阿木《ColorOS 16 / 17 Port for OnePlus 8T》

> 来源：https://github.com/daxiaamu/ColorOS-16-17-Port-for-8T
> 整理时间：2026-10-02
> 用途：本项目（ColorOS 16 → OPPO Find X2 Pro）与该 8T 移植项目做**方法论对齐与差异比对**。

---

## 一、最重要的结论：8T 的 ColorOS 16 **不是官方 OTA**

| 问题 | 结论 |
|---|---|
| 一加 8T 有官方 ColorOS 16 吗？ | **没有**。官方 ColorOS 16 覆盖「2022 年及之后发布」的机型（一加 10 Pro 起）；一加 9 系列、一加 10 标准版、初代 Ace 等 2021–2022 初机型被明确排除。8T 是 2020-10 机型，更不在列。 |
| 那用户手上的 8T ColorOS 16 包是什么？ | **第三方移植包**。本仓库即为其中之一：把 **Reno15c（PMD110）16.0.10.501** 的系统移植到 8T（KB2000）。 |
| OPPO Find X2 Pro 有官方 ColorOS 16 吗？ | **没有**。Find X2 Pro（2020-03）最后一次官方大版本是 **ColorOS 13 / Android 13**。ColorOS 官网升级计划里最老的机型是 Find N2（2022）/ Find X6（2023）/ 一加 11（2023）。 |
| 那我们做的是什么？ | **同一类工作**：把 8T 的 ColorOS 16 移植包再移植到同 SoC（kona / SM8250）的 Find X2 Pro。 |

## 二、方法论对齐（他们的原则 vs 我们的做法）

### 2.1 供体分层原则 —— 我们是对的 ✅

> 「**保留目标机的**：内核 / 设备树、vendor / odm、基带及对应固件；**供体提供**：较新系统框架与主要应用。」

设备实测完全吻合：

| 分区 | Find X2 Pro（目标机保留） | 供体 8T | 我们的处理 |
|---|---|---|---|
| vendor | **409 MB**（设备自己的） | 962 MB | 不动 ✅ |
| odm | **1.17 GB**（设备自己的） | 234 MB | 不动 ✅ |
| my_stock | **91 MB**（设备自己的） | 4.39 GB | 不动 ✅ |
| my_product | 1.44 GB | 1.44 GB（尺寸相同） | 不动 ✅ |
| system / system_ext / boot | — | — | **供体侧重建后刷入** ✅ |

> 他们另有一条警告：「供体 CPU 同属高通、大小核数量相同，**不能证明其 HAL / 显示 / 相机协议兼容**。」
> —— 我们的 ODM `subsys_daemon` 在 `libradioapis.so::QmiVsClient::getNecData` 崩溃，正是这一类。

### 2.2 APEX / EROFS —— 同一类根因，两种解法

| 维度 | 大侠阿木（8T） | 我们（Find X2 Pro） |
|---|---|---|
| 首障 | 旧内核不支持 APEX 内部 EROFS feature，日志 `unidentified incompatible feature 2` → `bootstrap-apexd-failed` | 完全相同（见 `05-分析/根因-A16-APEX-EROFS-big-pcluster-与-4.19.157-内核不兼容.md`） |
| 原则 | 「**先处理格式，而不是删 APEX 或关闭校验**」 | 同样选择重建 APEX 而非删包 |
| EROFS 构建参数 | `-z lz4hc,level=9 -C4096 -b4096 -E legacy-compress,^xattr-name-filter` | `-zlz4hc,level=9`（`incompat=0x1`）；带 `COMPR_CFGS` 的用 `-C16384` |
| 范围 | 「**逐个 APEX 单独判断**」，33 个容器、32 个需处理 | 完全一致：33 个中 32 个需处理 |
| 保留元数据 | 模块内容、标识、权限、**SELinux 标签**（xattr） | 一致（`--xattrs` + `#<标签模板>`） |
| 重建后 | 「**重新生成 AVB hashtree、项目签名及容器签名，签名之后复查 ZIP 对齐。不能把保留旧签名块当作重签成功**」 | **完全一致的教训**（第 6/7 号根因：APK Signature Scheme v2 签名块 + ZIP 对齐 `payload offset % 4096 == 0`） |

> ★ **值得试的一条**：他们的 `-E legacy-compress,^xattr-name-filter -C4096` 是**从构建参数上避免**新 incompat feature，
> 我们目前是「重建时把 incompat 降回 0x1」。两条路殊途同归，但他们的参数更显式、更可复现。
> 下一次重建 APEX 时值得对比验证。

### 2.3 我们踩到、他们文档没写的坑

他们的 `boot-and-build.md` **未涉及**：`boot cmdline`、`SELinux 策略`、`netd`、`netbpfload`、具体内核版本门限。
我们的独有发现（对他们也有参考价值）：

| # | 我们的根因 | 说明 |
|---|---|---|
| 3 | SELinux 三重障碍阻断 `apexd-bootstrap` | `buildvariant=user` 下 `setenforce` 编译期禁用 ⇒ 靠 boot cmdline `androidboot.selinux=permissive` 绕过 |
| 4 | netd 内核 5.4 硬门限（真凶 `0x4bc4`）| `"25Q2+ platform with kernel version < 5.4.0 is unsupported"` ⇒ NOP 三条门限 |
| 5 | netbpfload `4.19.236+` 硬门限 + xattr 丢失 | `0xbe5c` 门限；`--replace` 默认取树内同路径 xattr ⇒ `unlabeled` |
| 6/7 | `/system/apex/*` 与 `/system_ext/apex/*` 缺 v2 签名 | ★ `scanApexPackages` 扫**所有分区**的 `/apex/` |
| 8 | `/data/system/locksettings.db` 属主为 root | permissive 下仍 `Permission denied` ⇒ **一定是 DAC** |

> ★ **一个可能的差异解释**：他们为 8T **编译了配套内核（4.19.325）**（见仓库的 ReSukiSU 工作流），
> 而 **4.19.325 天然满足 netbpfload 的「4.19.236+」门限**；我们沿用 ColorOS 15 底座内核 **4.19.157**，所以必须打补丁。
> 这也解释了「供体能起、本机起不来」的决定性差异。

### 2.4 他们独有的坑（我们还没遇到，但值得警惕）

| 坑 | 现象 | 要点 |
|---|---|---|
| 符号链接被输出成文本 | 工具把 symlink 写成 `!<symlink>` 文本，被打进 `.so` ⇒ bad ELF，IMS/Atlas 反复崩 | 不能用空文件占位 |
| Windows `shutil.copytree` 丢链接语义 | `FILE_ATTRIBUTE_SYSTEM(4)` 变 `ARCHIVE(32)`，`mkfs.erofs` 把根目录 `init`/`bin` 打成普通文件 ⇒ 起不来；**刷写和读回哈希正确也发现不了** | 独立候选树里恢复 SYSTEM 属性后重建；**从 EROFS 直接审计**类型/链接目标 |
| DEX 版本 | 原包 DEX039，旧 smali 默认输出 DEX035 ⇒ 接口调用失败 | `smali --api 28` |
| APK 全量重建 | 旧脚本可能悄悄覆盖后续修复 | 只替换预期条目，比较 ZIP 条目差异集合 |
| EROFS 时间戳缓存 | 固定时间戳可能让解析缓存看见旧包 | 先核对磁盘哈希与实际运行代码 |
| `.fsv_meta` | 工具侧元数据，不是镜像内文件 | 以镜像解析为准 |
| 候选镜像管理 | 候选完成后**不可覆盖** | 明确 source → patched tree → candidate → installed → release 与哈希对应 |

## 三、对我们项目的可执行建议

1. **【高价值】试 `-E legacy-compress,^xattr-name-filter -C4096`** 重建 APEX，
   看能否减少对二进制门限补丁的依赖（至少让重建更规范）。
2. **【高价值】考虑换 4.19.325+ 内核**：可天然越过 netbpfload 门限，减少补丁面。
   （本项目已有 `03-脚本/build_hybrid_boot.py` / `build_hybrid_kernel.py` 做过 hybrid boot 探索。）
3. **【中】把他们的「候选镜像不可覆盖 + 哈希账本」规范引入**本项目（source → patched → candidate → installed → release）。
4. **【中】查他们的 `source-recipes.md`**（公开补丁工具与原创兼容片段），看有没有 netd/netbpfload 的现成配方。
5. **【低】符号链接审计**：我们的重建流程在 macOS 上不涉及 `!<symlink>`，但可以加一条
   「从 EROFS 反抽路径/类型/链接目标并比对」的断言（他们已经做到 4484 条路径一致）。
